Process states & PCB 7
OS-U1-Q01MCQeasy

In the classic five-state process model — New, Ready, Running, Waiting and Terminated — and assuming that no preemption occurs, which one of the following transitions is NOT part of the model?

  1. New → Ready
  2. Waiting → Ready
  3. Running → Waiting
  4. Running → Ready
Show answer & solution

Detailed solution

Concept. The five-state diagram has exactly these edges: New→Ready (admitted), Ready→Running (dispatched), Running→Waiting (a blocking request), Waiting→Ready (the event completes), Running→Terminated (exit). A process leaves the CPU only by blocking or by finishing.

Step by step.

  1. From Running the process either blocks (Running→Waiting) or exits (Running→Terminated).
  2. Without preemption nothing else can take the CPU away from a running process.
  3. So there is no edge from Running back to Ready.
  4. The edge Running→Ready appears only once preemption is added, giving the preemptive model.

Answer: Option (D) — Running → Ready is not an edge of the non-preemptive five-state model.

Why the other options are wrong.

  • (A) New→Ready is the admission transition.
  • (B) Waiting→Ready happens when the awaited event or I/O completes.
  • (C) Running→Waiting happens on a blocking request.

Common misconception. Students answer (B) because they think a blocked process resumes straight on the CPU. It always returns to Ready first and waits to be dispatched.

Takeaway. In the non-preemptive model the only exits from Running are Waiting and Terminated; Running→Ready exists only in a preemptive model.

OS-U1-Q02MCQeasy

Which one of the following is NOT stored in the process control block (PCB) of a process?

  1. The program counter and the saved contents of the CPU registers
  2. The process state and the scheduling priority
  3. The source code of the program
  4. The list of open files and the memory-management information
Show answer & solution

Detailed solution

Concept. A PCB is the kernel's record of a process: it holds everything the kernel needs to stop the process and later restart it. The program's code lives in the process's address space, not in the PCB.

Step by step.

  1. The PCB holds process identification (PID, parent PID) and process state.
  2. It holds saved CPU context: program counter, stack pointer and general-purpose registers.
  3. It holds scheduling information, memory-management information (page tables, base and limit registers) and I/O status such as the open-file table.
  4. The executable code and its data are mapped in the process's own address space, so the source code (or even the machine code) is not a PCB field.

Answer: Option (C) — the source code is not part of the PCB.

Why the other options are wrong.

  • (A) The saved register state is the heart of a PCB.
  • (B) Process state and priority are standard PCB fields.
  • (D) Open files and memory-management data are standard PCB fields.

Common misconception. The PCB is confused with the process image. The process image contains the code, the data and the stack; the PCB is a small kernel structure that points at them.

Takeaway. PCB = kernel bookkeeping (identity, state, context, scheduling, memory, I/O). The code and data belong to the address space.

OS-U1-Q03MCQmedium

A process in the Running state issues a blocking read on a disk file. In the five-state model, which sequence of transitions does it make before it can execute again?

  1. Running → Waiting, then Waiting → Ready
  2. Running → Ready, then Ready → Running
  3. Running → Waiting, then Waiting → Running
  4. Running → Terminated, then New → Ready
Show answer & solution

Detailed solution

Concept. A blocking system call moves the process from Running to Waiting. When the I/O completes the process is moved to Ready, and only the scheduler can then move it to Running.

Step by step.

  1. The read cannot complete immediately, so the process cannot keep the CPU: Running → Waiting.
  2. The disk controller interrupts when the data has arrived, and the interrupt handler moves the process from Waiting to Ready.
  3. The process now competes for the CPU like any other ready process; the dispatcher moves it Ready → Running.
  4. So the sequence is Running → Waiting → Ready → Running, which is option (A).

Answer: Option (A) — Running → Waiting, then Waiting → Ready.

Why the other options are wrong.

  • (B) skips the Waiting state altogether.
  • (C) has Waiting → Running, which never happens: a woken process must pass through Ready.
  • (D) terminates the process, but a completed read is not a failure.

Common misconception. The single most common error is Waiting → Running. There is no direct edge: every resumption goes through Ready, because the CPU may now be running something else.

Takeaway. Two rules to keep: a process enters Waiting only by its own blocking request, and it reaches Running only from Ready.

OS-U1-Q04MCQmedium

Which one of the following statements about a context switch is TRUE?

  1. It is pure overhead: no useful work of any user process is done while it executes.
  2. It saves the state of the outgoing process in the ready queue rather than in its PCB.
  3. It is needed every time a process makes a system call, even if no other process runs.
  4. Its cost is independent of the number of registers the CPU has.
Show answer & solution

Detailed solution

Concept. A context switch saves the CPU context of the outgoing process into its PCB and loads the context of the incoming process from its PCB. While the kernel does this, no user instruction executes, so the time is pure overhead.

Step by step.

  1. The kernel copies the program counter, stack pointer and registers into the PCB of the outgoing process.
  2. It then restores the same set of values from the PCB of the incoming process.
  3. During this interval no user process makes progress, so the cost is overhead, not work.
  4. The more registers the machine has, the more values must be copied, so the cost grows with the register file.

Answer: Option (A) — a context switch is pure overhead.

Why the other options are wrong.

  • (B) The saved state is written to the PCB; the ready queue only holds pointers to PCBs.
  • (C) A system call that does not cause a switch — a fast read from the page cache, for example — needs no context switch.
  • (D) Cost rises with the number of registers, not independently of it.

Common misconception. Students conflate a mode switch (user → kernel) with a context switch. A system call always causes a mode switch but only sometimes a context switch.

Takeaway. Context switch = save one PCB, restore another, no user work done. Mode switch alone is cheaper and much more frequent.

OS-U1-Q05MCQhard

In the seven-state process model, which adds Ready/Suspend and Blocked/Suspend, a process moves from Ready/Suspend to Ready when

  1. the event it was waiting for finally occurs.
  2. the scheduler dispatches it to the CPU.
  3. it is brought back from secondary storage into main memory.
  4. its parent process calls wait().
Show answer & solution

Detailed solution

Concept. The two suspended states describe a process that has been swapped out to secondary storage. Leaving a suspended state always means being swapped back into main memory; the suspend/activate transitions are about memory residency, not about events or scheduling.

Step by step.

  1. Ready/Suspend means the process is ready to run but its image is on disk.
  2. It cannot run until its image is back in main memory, so the transition Ready/Suspend → Ready is the activate operation performed by the swapper.
  3. Blocked/Suspend → Blocked is the same activate operation for a blocked process.
  4. The reverse transitions, Ready → Ready/Suspend and Blocked → Blocked/Suspend, are the suspend (swap-out) operations.

Answer: Option (C) — it is brought back from secondary storage into main memory.

Why the other options are wrong.

  • (A) The event completing moves Blocked/Suspend → Ready/Suspend, not Ready/Suspend → Ready.
  • (B) Dispatch is the Ready → Running transition.
  • (D) A parent's wait() has nothing to do with swapping a child back in.

Common misconception. The suspended states are read as 'waiting' states. They are not: they are memory-residency states. A ready process can be suspended, which is exactly why the state exists.

Takeaway. Suspended = swapped out. Leaving a suspended state = being swapped in. The event logic is carried entirely by the Blocked pair.

OS-U1-Q06MSQmedium

Which of the following statements about the process control block and process states are TRUE? (Select all that apply.)

  1. A PCB is created when the process is created and is kept in kernel memory.
  2. A process can move directly from the Waiting state to the Running state.
  3. The saved register state of a blocked process is kept in its PCB.
  4. The PCB of a process that is currently running must be in main memory.
Show answer & solution

Detailed solution

Concept. The PCB is the kernel's per-process record. It is allocated at creation, resides in kernel memory, and holds the saved context. State transitions always respect the diagram, so Waiting never goes straight to Running.

Step by step.

  1. (A) True: the PCB is created by the kernel when the process is admitted, and the kernel keeps it until the process is reaped.
  2. (B) False: a woken process goes Waiting → Ready and must then be dispatched Ready → Running.
  3. (C) True: the program counter, stack pointer and registers of a blocked process are exactly what the PCB stores so the process can be restarted later.
  4. (D) True: the running process is executing from main memory and its PCB is the kernel's live record of it, so that PCB is resident.

Answer: Options (A), (C) and (D).

Why the other options are wrong.

  • (B) is the classic invalid edge: Waiting → Running does not exist in any standard model.

Common misconception. Option (D) is often marked false by students who think PCBs can be paged out. A PCB may be swapped for a non-running process, but the PCB of the process that is executing right now is in main memory, because the kernel is using it.

Takeaway. Three facts worth memorising: one PCB per process, allocated at creation in kernel memory, holding the saved context that makes resumption possible.

OS-U1-Q07NATeasy

A process executes the following two statements, with no other process creation and no process terminating before the program ends:
fork();
fork();
Assuming both calls succeed, how many processes exist when the program reaches its end?
(Enter an integer.)

Show answer & solution

Detailed solution

Concept. fork() creates one child that is an exact copy of the caller, so every fork() call doubles the number of processes running that same code.

Step by step.

  1. Before the first call there is 1 process.
  2. The first fork() turns 1 process into 2; both continue to the second statement.
  3. The second fork() is executed by each of those 2 processes, so each creates one more: 2 + 2 = 4.
  4. Hence 4 processes exist at the end.

Answer: 4.

Common misconception. Counting only the children (3) instead of all processes (4). After n fork() calls there are 2ⁿ processes in total, not 2ⁿ − 1.

Takeaway. Each fork() doubles the process count: 1, 2, 4, 8 … for 1, 2, 3 successive calls.

Threads: user vs kernel 6
OS-U1-Q08MCQeasy

Which one of the following is TRUE of user-level threads?

  1. The kernel schedules each thread of the process separately.
  2. A blocking system call made by one thread blocks every thread in that process.
  3. They cannot be created unless the operating system provides a thread library in the kernel.
  4. Each thread has its own private address space.
Show answer & solution

Detailed solution

Concept. With user-level threads the kernel sees only one process and one schedulable entity. The thread library multiplexes several threads onto that single kernel entity, so the kernel cannot tell them apart.

Step by step.

  1. Because the kernel knows only the process, it schedules the process, not the threads.
  2. When one user-level thread makes a blocking system call, the kernel blocks the whole process, so every thread in it stops.
  3. No kernel thread support is needed at all — that is the point of user-level threads.
  4. Threads of one process share the address space; only their stacks and registers differ.

Answer: Option (B) — a blocking call by one user-level thread blocks the whole process.

Why the other options are wrong.

  • (A) The kernel schedules the process as a single entity.
  • (C) User-level threads need no kernel support; the library does all the work.
  • (D) Threads share one address space; that is what makes them cheap.

Common misconception. Students assume threads are always independently schedulable. That is only true when the threads are kernel-level.

Takeaway. User-level threads: fast, no kernel involvement, but one blocking call stalls them all. Kernel-level threads: independently schedulable, but heavier.

OS-U1-Q09MCQeasy

Which one of the following is shared by all threads of the same process?

  1. The stack
  2. The program counter
  3. The set of CPU registers
  4. The heap and the global data segment
Show answer & solution

Detailed solution

Concept. Threads are the unit of execution; a process is the unit of resource ownership. Everything that is a resource — code, global data, heap, open files — is shared; everything that is execution state — stack, registers, program counter — is private.

Step by step.

  1. Each thread needs its own stack to hold its own local variables and call frames.
  2. Each thread needs its own program counter, because the threads are at different points in the code.
  3. Each thread needs its own register set for the same reason.
  4. The heap and global data are resources of the process and are shared by every thread, which is why unsynchronised access to them causes data races.

Answer: Option (D) — the heap and the global data segment.

Why the other options are wrong.

  • (A), (B) and (C) are all per-thread execution state.

Common misconception. The heap is often assumed to be per-thread because malloc is called per thread. malloc is thread-safe but the heap itself is one shared arena.

Takeaway. Shared: code, globals, heap, files. Private: stack, registers, program counter. That single split answers most thread questions.

OS-U1-Q10MCQmedium

Which threading model cannot exploit a multicore processor, however many threads the process creates?

  1. Many-to-one
  2. One-to-one
  3. Many-to-many
  4. Both many-to-one and many-to-many
Show answer & solution

Detailed solution

Concept. Parallel execution on several cores requires several kernel-schedulable entities. The many-to-one model maps every user thread onto a single kernel thread, so at most one thread can be on a CPU at any instant.

Step by step.

  1. Many-to-one: all user threads share one kernel thread, so the kernel can place that one entity on at most one core.
  2. One-to-one: each user thread has its own kernel thread, so the kernel can spread them across cores.
  3. Many-to-many: several user threads map onto a smaller set of kernel threads, but that set can still be larger than one, so parallelism is possible.
  4. Only many-to-one is strictly limited to a single core.

Answer: Option (A) — many-to-one.

Why the other options are wrong.

  • (B) One-to-one supports true parallelism.
  • (C) Many-to-many supports parallelism as long as more than one kernel thread is used.
  • (D) is wrong because many-to-many can use several cores.

Common misconception. Students pick many-to-many because they reason that the multiplexing must serialise the threads. Multiplexing limits the degree of parallelism; it does not force it to one.

Takeaway. Parallelism needs more than one kernel thread. Many-to-one has exactly one, so it is confined to a single core.

OS-U1-Q11MSQmedium

Which of the following statements about user-level and kernel-level threads are TRUE? (Select all that apply.)

  1. Kernel-level threads of one process can execute in parallel on different cores of a multiprocessor.
  2. Creating a user-level thread is typically cheaper than creating a kernel-level thread.
  3. If one kernel-level thread of a process blocks in a system call, all the other threads of that process block as well.
  4. Switching between two user-level threads of the same process does not require a switch to kernel mode.
Show answer & solution

Detailed solution

Concept. Kernel-level threads are separate schedulable entities, so the kernel can run them on different cores and block one without blocking the others. User-level threads are managed entirely inside the process, which makes creation and switching cheap.

Step by step.

  1. (A) True: each kernel thread can be dispatched to a different core.
  2. (B) True: a user-level thread needs only a stack and a small control block allocated by the library, with no kernel trap.
  3. (C) False: the kernel blocks only the thread that made the call; the other threads of the process stay runnable.
  4. (D) True: the library saves and restores registers in user space, so no trap occurs.

Answer: Options (A), (B) and (D).

Why the other options are wrong.

  • (C) describes the many-to-one, user-level situation, not kernel-level threads.

Common misconception. Option (C) is the exact property that separates the two kinds of thread, and it is sometimes attached to the wrong kind.

Takeaway. Kernel-level: block one, the others run. User-level: block one, block all — but creation and switching are much cheaper.

OS-U1-Q12MCQhard

A process uses a many-to-one user-level thread library whose scheduler is non-preemptive. It has three threads, and one of them enters a long computation that contains no system call and never yields. Which one of the following is TRUE?

  1. All three threads continue to make progress, because the kernel time-slices them.
  2. The computing thread keeps the CPU and the other two threads never run.
  3. The kernel preempts the computing thread after one time quantum and schedules another thread of the process.
  4. The other two threads run on other cores of the processor.
Show answer & solution

Detailed solution

Concept. In many-to-one, the kernel schedules one entity — the process. The thread library schedules the threads inside that entity, and a non-preemptive library can only switch when the running thread yields or blocks.

Step by step.

  1. The kernel sees a single schedulable entity and can only preempt that entity, not the individual threads inside it.
  2. A timer interrupt therefore returns control to the same thread, because the library's dispatcher is never entered.
  3. The computing thread makes no system call and never yields, so the library never gets a chance to switch.
  4. The other two threads remain ready inside the library and never execute.

Answer: Option (B) — the computing thread keeps the CPU and the other two threads never run.

Why the other options are wrong.

  • (A) The kernel cannot time-slice threads it does not know about.
  • (C) A quantum expiry re-enters the same thread; the library scheduler is not invoked.
  • (D) Many-to-one uses one kernel thread, so only one core can be used.

Common misconception. Students assume a non-preemptive library is safe because the OS preempts the process. The OS does preempt the process, but it resumes the same thread.

Takeaway. A non-preemptive user-level scheduler makes cooperative multitasking mandatory: a thread that never yields starves its siblings.

OS-U1-Q13NATeasy

A process starts with a single thread and then creates four more threads with pthread_create. Each thread, including the original one, is given its own stack by the thread library. How many distinct thread stacks exist in the process?
(Enter an integer.)

Show answer & solution

Detailed solution

Concept. Every thread of a process has a private stack, because each needs its own call frames and local variables. The count of stacks therefore equals the count of threads.

Step by step.

  1. The process begins with 1 thread, which already has a stack.
  2. Four more threads are created, each with a new stack.
  3. Total threads = 1 + 4 = 5.
  4. Total stacks = 5, one per thread.

Answer: 5.

Common misconception. Answering 4 by counting only the newly created threads. The original thread has a stack too, so the total is threads, not creations.

Takeaway. Stacks are per thread; the heap and the code are per process. One stack per thread, always.

Preemptive vs non-preemptive 5
OS-U1-Q14MCQeasy

Which one of the following CPU scheduling algorithms is inherently non-preemptive?

  1. Round robin
  2. Shortest remaining time first
  3. First come first served
  4. Preemptive priority scheduling
Show answer & solution

Detailed solution

Concept. Preemption needs a rule that can remove a running process. FCFS has none: it dispatches the oldest ready process and lets it run until it blocks or terminates.

Step by step.

  1. FCFS hands the CPU to the process that arrived earliest and never takes it back; the only exits are blocking and termination.
  2. Round robin preempts on quantum expiry — that is its whole mechanism.
  3. SRTF preempts whenever a new arrival has a shorter remaining time.
  4. Preemptive priority preempts whenever a higher-priority process becomes ready.

Answer: Option (C) — first come first served.

Why the other options are wrong.

  • (A), (B) and (D) are all defined by their preemption rule.

Common misconception. Students sometimes call FCFS preemptive because an arriving process with a short burst 'should' run first. FCFS ignores burst lengths entirely.

Takeaway. Non-preemptive algorithms in the GATE syllabus: FCFS and non-preemptive SJF. Everything with 'remaining time', a quantum, or a preemptive priority is preemptive.

OS-U1-Q15MCQmedium

Which one of the following does NOT by itself cause the running process to be preempted?

  1. The interval timer expires the running process's time quantum.
  2. A process with a higher priority becomes ready.
  3. The I/O request of a blocked process completes, so that process becomes ready.
  4. Under SRTF, a newly arrived process has a shorter remaining burst than the running process.
Show answer & solution

Detailed solution

Concept. Preemption means the running process is displaced by the scheduler's policy. A process merely becoming ready is not enough; the policy must also rank it above the running one.

Step by step.

  1. (A) Quantum expiry is the round-robin preemption trigger.
  2. (B) Under preemptive priority a higher-priority arrival outranks the running process, so it preempts.
  3. (C) I/O completion only moves a process from Waiting to Ready. Whether it then preempts depends on the policy; in FCFS or non-preemptive SJF it simply waits.
  4. (D) SRTF compares remaining times, so a shorter newcomer does preempt.

Answer: Option (C) — an I/O completion by itself does not preempt.

Why the other options are wrong.

  • (A), (B) and (D) are each a defined preemption trigger under the stated policy.

Common misconception. Students treat 'becomes ready' as synonymous with 'preempts'. Becoming ready is a state change; preemption is a scheduling decision on top of it.

Takeaway. Ask which policy is in force. A ready process preempts only if that policy ranks it above the running one.

Which of the following scheduling algorithms can be preemptive? (Select all that apply.)

  1. Shortest remaining time first (SRTF)
  2. Round robin
  3. Non-preemptive shortest job first (SJF)
  4. Priority scheduling in its preemptive form
Show answer & solution

Detailed solution

Concept. An algorithm is preemptive if it can remove a running process before that process blocks or finishes. SRTF compares remaining times, round robin uses a quantum, and preemptive priority compares priorities — all three can displace a running process.

Step by step.

  1. (A) SRTF is preemptive by definition: the shortest remaining time always runs.
  2. (B) Round robin preempts on quantum expiry.
  3. (C) Non-preemptive SJF, as its name states, lets the chosen job run to completion.
  4. (D) The preemptive form of priority scheduling displaces the running process when a higher-priority process becomes ready.

Answer: Options (A), (B) and (D).

Why the other options are wrong.

  • (C) is explicitly non-preemptive; SJF has a separate preemptive version called SRTF.

Common misconception. SJF and SRTF are treated as one algorithm, so SJF is marked preemptive. They are two algorithms: SJF is non-preemptive, SRTF is its preemptive counterpart.

Takeaway. SJF ↔ SRTF is the standard non-preemptive/preemptive pair. Priority scheduling has the same pair, and round robin is preemptive by construction.

OS-U1-Q17MSQeasy

Under non-preemptive scheduling, which of the following can take the CPU away from the running process? (Select all that apply.)

  1. The process terminates.
  2. The process issues a blocking I/O request.
  3. A process with a higher priority arrives in the ready queue.
  4. The process's time quantum expires.
Show answer & solution

Detailed solution

Concept. In a non-preemptive scheme the running process gives up the CPU voluntarily. Only two events are voluntary: finishing, and blocking on something.

Step by step.

  1. (A) Termination releases the CPU, so the scheduler picks the next process.
  2. (B) A blocking request moves the process to Waiting and releases the CPU.
  3. (C) A higher-priority arrival is exactly what preemption would act on — and non-preemptive scheduling refuses to act.
  4. (D) There is no time quantum to expire in a non-preemptive algorithm.

Answer: Options (A) and (B).

Why the other options are wrong.

  • (C) is the definition of preemption, which is absent here.
  • (D) A quantum belongs to round robin, which is preemptive.

Common misconception. Option (D) is chosen because students think every algorithm has a quantum. A quantum is a round-robin parameter, not a universal one.

Takeaway. Non-preemptive = the process keeps the CPU until it blocks or exits. Nothing else can take it away.

Detailed solution

Concept. Preemptive priority compares the priority of the running process with that of every ready process, at every arrival. A preemption happens only when the newcomer outranks the process currently on the CPU.

Step by step.

  1. t = 0: only P1 has arrived, so P1 runs.
  2. t = 2: P2 (priority 1) arrives and outranks P1 (priority 5) — P1 is preempted. Preemption 1. P2 runs for its 1 ms and finishes at t = 3.
  3. t = 3: P1 is the only ready process, so P1 resumes and runs from t = 3.
  4. t = 4: P3 (priority 2) arrives and outranks P1 (priority 5) — P1 is preempted. Preemption 2. P3 runs 1 ms and finishes at t = 5; P1 resumes.
  5. t = 6: P4 (priority 3) arrives and outranks P1 (priority 5) — P1 is preempted. Preemption 3. P4 runs 1 ms and finishes at t = 7.
  6. t = 7: P1 runs its remaining 17 ms and finishes at t = 23.
  7. Total preemptions = 3.

Answer: 3.

Common misconception. Counting the dispatches of P3 and P4 as preemptions is right here only because P1 happened to be running each time. The trap is the opposite error: counting a preemption when the CPU was idle or when a process had just finished, which is a fresh dispatch, not a preemption.

Takeaway. A preemption needs a victim that is actually running. Trace the timeline second by second and ask, at each arrival, whether the newcomer outranks whoever holds the CPU.

Detailed solution

Concept. Under FCFS the processes run in arrival order without interruption. Waiting time is turnaround time minus burst time, and turnaround time is completion time minus arrival time.

Step by step.

  1. P1 runs from 0 to 3: completion 3, waiting time 3 − 0 − 3 = 0.
  2. P2 runs from 3 to 9: completion 9, waiting time 9 − 1 − 6 = 2.
  3. P3 runs from 9 to 13: completion 13, waiting time 13 − 2 − 4 = 7.
  4. Average = (0 + 2 + 7) / 3 = 9 / 3 = 3 ms.

Answer: Option (A) — 3 ms.

Why the other options are wrong.

  • (B) comes from forgetting to subtract the arrival time of P2 and P3.
  • (C) and (D) come from adding arrival times instead of subtracting them.

Common misconception. Using arrival time as the start time for every process. P2 does not start at t = 1; it starts when P1 releases the CPU.

Takeaway. Waiting time = completion − arrival − burst. Always compute completion times first.

OS-U1-Q20MCQeasy

The convoy effect — several short CPU-bound processes queued behind one long CPU-bound process, producing a poor average waiting time — is most closely associated with which algorithm?

  1. Round robin
  2. First come first served
  3. Shortest remaining time first
  4. Multilevel feedback queue
Show answer & solution

Detailed solution

Concept. The convoy effect is a direct consequence of serving processes in arrival order regardless of length, which is exactly what FCFS does.

Step by step.

  1. Under FCFS one long job at the head of the queue makes every short job behind it wait.
  2. The short jobs also hold up the I/O device they use only briefly, so device utilisation suffers too.
  3. SRTF would move the short jobs ahead, and round robin would interleave them, so neither produces the convoy.
  4. Hence the convoy effect belongs to FCFS.

Answer: Option (B) — first come first served.

Why the other options are wrong.

  • (A) Round robin interleaves jobs and bounds the wait by the quantum.
  • (C) SRTF always runs the shortest remaining job, which dissolves the convoy.
  • (D) Multilevel feedback queues promote short jobs, which also dissolves it.

Common misconception. The convoy effect is sometimes attached to SJF because SJF is 'the fix'. SJF avoids the convoy; FCFS causes it.

Takeaway. Convoy effect = FCFS + one long job at the head. The standard remedies are SJF, SRTF and round robin.

OS-U1-Q21MCQmedium

Three processes arrive at time t = 0 with CPU bursts of 12 ms, 18 ms and 30 ms. The scheduler knows the burst lengths in advance. What is the minimum achievable average waiting time for these three processes under a non-preemptive scheduler?

  1. 12 ms
  2. 14 ms
  3. 16 ms
  4. 18 ms
Show answer & solution

Detailed solution

Concept. For a fixed set of processes with no arrival spread, the non-preemptive algorithm that minimises average waiting time is shortest job first: run the shortest burst first and the longest last.

Step by step.

  1. Order the bursts: 12, 18, 30.
  2. SJF runs them in that order. Waiting times: first job 0, second 12, third 12 + 18 = 30.
  3. Average = (0 + 12 + 30) / 3 = 42 / 3 = 14 ms.
  4. Any other order increases the sum, so 14 ms is the minimum.

Answer: Option (B) — 14 ms.

Why the other options are wrong.

  • (A) 12 ms is the waiting time of the second job alone.
  • (C) and (D) come from averaging turnaround times, or from running the jobs in arrival order and dividing incorrectly.

Common misconception. Averaging turnaround times instead of waiting times. With all arrivals at t = 0 the turnaround times are 12, 30, 60, whose average is 34 ms — a different quantity.

Takeaway. All arriving together + non-preemptive + 'minimum average waiting time' means sort the bursts ascending and accumulate: 0, b₁, b₁ + b₂.

  1. t = 0–2: P1 runs its first quantum, 2 ms, leaving 3 ms. P2 arrived at t = 1 and is already queued.

OS-U1-Q23MSQhard

Which of the following statements about CPU scheduling algorithms are TRUE? (Select all that apply.)

  1. SRTF can starve a long process indefinitely if short processes keep arriving.
  2. Increasing the time quantum of round robin increases the number of context switches.
  3. Among non-preemptive algorithms, SJF minimises the average waiting time.
  4. FCFS always gives the minimum average turnaround time for a given set of processes.
Show answer & solution

Detailed solution

Concept. Starvation, quantum size and SJF optimality are the three classic scheduling properties; FCFS optimality is the classic false claim.

Step by step.

  1. (A) True: SRTF always picks the shortest remaining time, so a long job loses to every short arrival and may never run.
  2. (B) False: a larger quantum means fewer expiries, hence fewer context switches — with a quantum larger than every burst, round robin degenerates into FCFS.
  3. (C) True: SJF is provably optimal for average waiting time among non-preemptive algorithms, by an exchange argument on adjacent jobs.
  4. (D) False: FCFS can be arbitrarily bad — the convoy effect — so it cannot be optimal.

Answer: Options (A) and (C).

Why the other options are wrong.

  • (B) reverses the relationship: the number of switches falls as the quantum grows.
  • (D) is false; SJF, not FCFS, is the optimal non-preemptive rule for waiting time.

Common misconception. Option (B) is chosen because a smaller quantum is associated with 'more responsive', which students turn into 'more switches when the quantum grows'. It is the other way round.

Takeaway. Quantum up → switches down, response worse. Quantum down → switches up, overhead up. SJF is optimal for waiting time; nothing is optimal for turnaround in general except in special cases.

Concept. Under SRTF the process with the smallest remaining burst always holds the CPU, and the comparison is repeated at every arrival. Waiting time = completion − arrival − burst.

Step by step.

  1. t = 0: P1 runs. At t = 2 its remaining time is 5.
  2. t = 2: P2 arrives with burst 4 < 5, so P2 preempts P1.
  3. t = 4: P3 arrives with burst 1 < P2's remaining 2, so P3 preempts P2.
  4. t = 5: P3 completes. Remaining: P2 = 2, P1 = 5, P4 = 4 (P4 arrived at t = 5). P2 runs.
  5. t = 7: P2 completes. Remaining: P4 = 4, P1 = 5. P4 runs.
  6. t = 11: P4 completes. P1 runs its remaining 5 ms and completes at t = 16.
  7. Completion times: P1 = 16, P2 = 7, P3 = 5, P4 = 11.
  8. Waiting times: P1 = 16 − 0 − 7 = 9; P2 = 7 − 2 − 4 = 1; P3 = 5 − 4 − 1 = 0; P4 = 11 − 5 − 4 = 2.
  9. Average = (9 + 1 + 0 + 2) / 4 = 12 / 4 = 3 ms.

Answer: 3 ms.

Common misconception. Letting P1 finish its first stretch because it started first. SRTF is preemptive: P2's burst of 4 beats P1's remaining 5 at t = 2, so P1 is displaced.

Takeaway. Re-evaluate the shortest remaining time at every arrival instant, not only at completions.

Detailed solution

Concept. Turnaround time is completion time minus arrival time; it includes both the waiting and the execution of the process. Under SRTF the schedule is rebuilt at every arrival.

Step by step.

  1. t = 0: P1 runs. At t = 1 its remaining time is 5.
  2. t = 1: P2 arrives with burst 2 < 5, so P2 preempts P1.
  3. t = 2: P3 arrives with burst 1, which ties P2's remaining time of 1. The running process P2 continues (the tie does not change the totals either way).
  4. t = 3: P2 completes. Ready: P3 = 1, P4 = 3 (arrived at t = 3), P1 = 5. P3 runs.
  5. t = 4: P3 completes. P4 = 3 < P1 = 5, so P4 runs from t = 4 to t = 7.
  6. t = 7: P4 completes. P1 runs its remaining 5 ms and completes at t = 12.
  7. Completion times: P1 = 12, P2 = 3, P3 = 4, P4 = 7.
  8. Turnaround times: P1 = 12 − 0 = 12; P2 = 3 − 1 = 2; P3 = 4 − 2 = 2; P4 = 7 − 3 = 4.
  9. Average = (12 + 2 + 2 + 4) / 4 = 20 / 4 = 5 ms.

Answer: 5 ms.

Common misconception. Reporting the average waiting time instead. Here the waiting times are 6, 0, 1, 1, whose average is 2 ms — a different number, and the usual wrong answer.

Takeaway. Turnaround = completion − arrival. Waiting = turnaround − burst. Read which one the question asks for before dividing.
