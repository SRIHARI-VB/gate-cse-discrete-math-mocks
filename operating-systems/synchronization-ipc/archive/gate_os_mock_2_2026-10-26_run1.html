OS-U1-Q01MCQeasy

In the classic five-state process model — New, Ready, Running, Waiting and Terminated — and assuming that no preemption occurs, which one of the following transitions is NOT part of the model?

  1. New → Ready
  2. Waiting → Ready
  3. Running → Waiting
  4. Running → Ready
Show answer & solution

Detailed solution

Concept. The five-state diagram has exactly these edges: New→Ready (admitted), Ready→Running (dispatched), Running→Waiting (a blocking request), Waiting→Ready (the event completes), Running→Terminated (exit). A process leaves the CPU only by blocking or by finishing.

Step by step.

  1. From Running the process either blocks (Running→Waiting) or exits (Running→Terminated).
  2. Without preemption nothing else can take the CPU away from a running process.
  3. So there is no edge from Running back to Ready.
  4. The edge Running→Ready appears only once preemption is added, giving the preemptive model.

Answer: Option (D) — Running → Ready is not an edge of the non-preemptive five-state model.

Why the other options are wrong.

  • (A) New→Ready is the admission transition.
  • (B) Waiting→Ready happens when the awaited event or I/O completes.
  • (C) Running→Waiting happens on a blocking request.

Common misconception. Students answer (B) because they think a blocked process resumes straight on the CPU. It always returns to Ready first and waits to be dispatched.

Takeaway. In the non-preemptive model the only exits from Running are Waiting and Terminated; Running→Ready exists only in a preemptive model.

OS-U1-Q02MCQeasy

Which one of the following is NOT stored in the process control block (PCB) of a process?

  1. The program counter and the saved contents of the CPU registers
  2. The process state and the scheduling priority
  3. The source code of the program
  4. The list of open files and the memory-management information
Show answer & solution

Detailed solution

Concept. A PCB is the kernel's record of a process: it holds everything the kernel needs to stop the process and later restart it. The program's code lives in the process's address space, not in the PCB.

Step by step.

  1. The PCB holds process identification (PID, parent PID) and process state.
  2. It holds saved CPU context: program counter, stack pointer and general-purpose registers.
  3. It holds scheduling information, memory-management information (page tables, base and limit registers) and I/O status such as the open-file table.
  4. The executable code and its data are mapped in the process's own address space, so the source code (or even the machine code) is not a PCB field.

Answer: Option (C) — the source code is not part of the PCB.

Why the other options are wrong.

  • (A) The saved register state is the heart of a PCB.
  • (B) Process state and priority are standard PCB fields.
  • (D) Open files and memory-management data are standard PCB fields.

Common misconception. The PCB is confused with the process image. The process image contains the code, the data and the stack; the PCB is a small kernel structure that points at them.

Takeaway. PCB = kernel bookkeeping (identity, state, context, scheduling, memory, I/O). The code and data belong to the address space.

OS-U1-Q03MCQmedium

A process in the Running state issues a blocking read on a disk file. In the five-state model, which sequence of transitions does it make before it can execute again?

  1. Running → Waiting, then Waiting → Ready
  2. Running → Ready, then Ready → Running
  3. Running → Waiting, then Waiting → Running
  4. Running → Terminated, then New → Ready
Show answer & solution

Detailed solution

Concept. A blocking system call moves the process from Running to Waiting. When the I/O completes the process is moved to Ready, and only the scheduler can then move it to Running.

Step by step.

  1. The read cannot complete immediately, so the process cannot keep the CPU: Running → Waiting.
  2. The disk controller interrupts when the data has arrived, and the interrupt handler moves the process from Waiting to Ready.
  3. The process now competes for the CPU like any other ready process; the dispatcher moves it Ready → Running.
  4. So the sequence is Running → Waiting → Ready → Running, which is option (A).

Answer: Option (A) — Running → Waiting, then Waiting → Ready.

Why the other options are wrong.

  • (B) skips the Waiting state altogether.
  • (C) has Waiting → Running, which never happens: a woken process must pass through Ready.
  • (D) terminates the process, but a completed read is not a failure.

Common misconception. The single most common error is Waiting → Running. There is no direct edge: every resumption goes through Ready, because the CPU may now be running something else.

Takeaway. Two rules to keep: a process enters Waiting only by its own blocking request, and it reaches Running only from Ready.

OS-U1-Q04MCQmedium

Which one of the following statements about a context switch is TRUE?

  1. It is pure overhead: no useful work of any user process is done while it executes.
  2. It saves the state of the outgoing process in the ready queue rather than in its PCB.
  3. It is needed every time a process makes a system call, even if no other process runs.
  4. Its cost is independent of the number of registers the CPU has.
Show answer & solution

Detailed solution

Concept. A context switch saves the CPU context of the outgoing process into its PCB and loads the context of the incoming process from its PCB. While the kernel does this, no user instruction executes, so the time is pure overhead.

Step by step.

  1. The kernel copies the program counter, stack pointer and registers into the PCB of the outgoing process.
  2. It then restores the same set of values from the PCB of the incoming process.
  3. During this interval no user process makes progress, so the cost is overhead, not work.
  4. The more registers the machine has, the more values must be copied, so the cost grows with the register file.

Answer: Option (A) — a context switch is pure overhead.

Why the other options are wrong.

  • (B) The saved state is written to the PCB; the ready queue only holds pointers to PCBs.
  • (C) A system call that does not cause a switch — a fast read from the page cache, for example — needs no context switch.
  • (D) Cost rises with the number of registers, not independently of it.

Common misconception. Students conflate a mode switch (user → kernel) with a context switch. A system call always causes a mode switch but only sometimes a context switch.

Takeaway. Context switch = save one PCB, restore another, no user work done. Mode switch alone is cheaper and much more frequent.

OS-U1-Q05MCQhard

In the seven-state process model, which adds Ready/Suspend and Blocked/Suspend, a process moves from Ready/Suspend to Ready when

  1. the event it was waiting for finally occurs.
  2. the scheduler dispatches it to the CPU.
  3. it is brought back from secondary storage into main memory.
  4. its parent process calls wait().
Show answer & solution

Detailed solution

Concept. The two suspended states describe a process that has been swapped out to secondary storage. Leaving a suspended state always means being swapped back into main memory; the suspend/activate transitions are about memory residency, not about events or scheduling.

Step by step.

  1. Ready/Suspend means the process is ready to run but its image is on disk.
  2. It cannot run until its image is back in main memory, so the transition Ready/Suspend → Ready is the activate operation performed by the swapper.
  3. Blocked/Suspend → Blocked is the same activate operation for a blocked process.
  4. The reverse transitions, Ready → Ready/Suspend and Blocked → Blocked/Suspend, are the suspend (swap-out) operations.

Answer: Option (C) — it is brought back from secondary storage into main memory.

Why the other options are wrong.

  • (A) The event completing moves Blocked/Suspend → Ready/Suspend, not Ready/Suspend → Ready.
  • (B) Dispatch is the Ready → Running transition.
  • (D) A parent's wait() has nothing to do with swapping a child back in.

Common misconception. The suspended states are read as 'waiting' states. They are not: they are memory-residency states. A ready process can be suspended, which is exactly why the state exists.

Takeaway. Suspended = swapped out. Leaving a suspended state = being swapped in. The event logic is carried entirely by the Blocked pair.

OS-U1-Q06MSQmedium

Which of the following statements about the process control block and process states are TRUE? (Select all that apply.)

  1. A PCB is created when the process is created and is kept in kernel memory.
  2. A process can move directly from the Waiting state to the Running state.
  3. The saved register state of a blocked process is kept in its PCB.
  4. The PCB of a process that is currently running must be in main memory.
Show answer & solution

Detailed solution

Concept. The PCB is the kernel's per-process record. It is allocated at creation, resides in kernel memory, and holds the saved context. State transitions always respect the diagram, so Waiting never goes straight to Running.

Step by step.

  1. (A) True: the PCB is created by the kernel when the process is admitted, and the kernel keeps it until the process is reaped.
  2. (B) False: a woken process goes Waiting → Ready and must then be dispatched Ready → Running.
  3. (C) True: the program counter, stack pointer and registers of a blocked process are exactly what the PCB stores so the process can be restarted later.
  4. (D) True: the running process is executing from main memory and its PCB is the kernel's live record of it, so that PCB is resident.

Answer: Options (A), (C) and (D).

Why the other options are wrong.

  • (B) is the classic invalid edge: Waiting → Running does not exist in any standard model.

Common misconception. Option (D) is often marked false by students who think PCBs can be paged out. A PCB may be swapped for a non-running process, but the PCB of the process that is executing right now is in main memory, because the kernel is using it.

Takeaway. Three facts worth memorising: one PCB per process, allocated at creation in kernel memory, holding the saved context that makes resumption possible.

OS-U1-Q07NATeasy

A process executes the following two statements, with no other process creation and no process terminating before the program ends:
fork();
fork();
Assuming both calls succeed, how many processes exist when the program reaches its end?
(Enter an integer.)

Show answer & solution

Detailed solution

Concept. fork() creates one child that is an exact copy of the caller, so every fork() call doubles the number of processes running that same code.

Step by step.

  1. Before the first call there is 1 process.
  2. The first fork() turns 1 process into 2; both continue to the second statement.
  3. The second fork() is executed by each of those 2 processes, so each creates one more: 2 + 2 = 4.
  4. Hence 4 processes exist at the end.

Answer: 4.

Common misconception. Counting only the children (3) instead of all processes (4). After n fork() calls there are 2ⁿ processes in total, not 2ⁿ − 1.

Takeaway. Each fork() doubles the process count: 1, 2, 4, 8 … for 1, 2, 3 successive calls.

OS-U1-Q26MCQeasy

The CPU scheduler picks a process and the dispatcher hands the CPU over to it. Which one of the following is performed by the dispatcher and not by the CPU scheduler?

  1. Choosing the next process to run from among the ready processes
  2. Saving the context of the outgoing process, switching to user mode and jumping to the proper location in the incoming program
  3. Deciding how many processes are admitted into main memory
  4. Deciding whether the running process should be preempted
Show answer & solution

Detailed solution

Concept. The short-term scheduler selects; the dispatcher performs the switch. The dispatcher does three things — save the context of the outgoing process, switch from kernel to user mode, and jump to the proper location in the new program. The time taken to stop one process and start another is the dispatch latency.

Step by step.

  1. Selecting the victim or the successor is the scheduler's job, so option (A) belongs to the scheduler.
  2. The context save and the jump into the new program are the dispatcher's three actions, which is exactly option (B).
  3. Admission of processes is the long-term scheduler's decision, not the dispatcher's.
  4. The preemption decision is part of the scheduling policy.

Answer: Option (B) — the dispatcher saves the context, switches to user mode and jumps into the incoming program.

Why the other options are wrong.

  • (A) is the short-term scheduler's selection step.
  • (C) is the long-term scheduler's admission decision.
  • (D) is the preemption policy, which the scheduler applies.

Common misconception. Treating "scheduler" and "dispatcher" as synonyms. The scheduler is a policy that chooses; the dispatcher is the mechanism that switches. Dispatch latency is a cost of the mechanism, not of the policy.

Takeaway. Whenever a question asks what a context switch costs, it is asking about dispatcher work — and that work does no useful work for any user process.

OS-U1-Q27MCQeasy

Which one of the following quantities is controlled by the long-term scheduler?

  1. The degree of multiprogramming, i.e. how many processes are in main memory at once
  2. The order in which ready processes are dispatched to the CPU
  3. The number of context switches performed per second
  4. The length of the time quantum given to each process
Show answer & solution

Detailed solution

Concept. The long-term scheduler decides which programs are admitted to the ready queue and therefore fixes the degree of multiprogramming. It should admit a good mix of I/O-bound and CPU-bound processes, because too many CPU-bound processes leave the I/O devices idle.

Step by step.

  1. The long-term scheduler admits a process into main memory; the count of admitted processes is the degree of multiprogramming, so (A) is its decision.
  2. The order of dispatch among ready processes is the short-term scheduler's decision.
  3. The number of context switches follows from the short-term policy and the quantum, not from admission.
  4. The quantum is a parameter of the short-term policy.

Answer: Option (A) — the long-term scheduler controls the degree of multiprogramming.

Why the other options are wrong.

  • (B) belongs to the short-term scheduler.
  • (C) and (D) are consequences of the short-term policy.

Common misconception. Believing the medium-term scheduler also raises the degree of multiprogramming. It does the opposite: by swapping a process out it reduces the degree of multiprogramming.

Takeaway. Three schedulers, three questions: long-term = how many, medium-term = how many stay in memory, short-term = which one runs now.

OS-U1-Q28MCQmedium

A running process calls exec() successfully. Which one of the following is preserved across that call?

  1. The process identifier (PID)
  2. The contents of the process's heap and data segment
  3. The values that the general-purpose registers held at the moment of the call
  4. The instruction at which the process had been executing
Show answer & solution

Detailed solution

Concept. exec() overwrites the process image — code, data, heap and stack — with the new program. What survives is the process's identity and its kernel-side bookkeeping: the PID, the parent relationship, the priority and, unless marked close-on-exec, the open file descriptors.

Step by step.

  1. The PID is assigned at fork() and is not changed by exec(), so it survives — option (A).
  2. The heap and data segment belong to the old program image and are discarded.
  3. The registers are reinitialised for the new program's entry point.
  4. Execution restarts at the new program's entry point, so the old instruction is gone.

Answer: Option (A) — the PID is preserved; the process image is replaced.

Why the other options are wrong.

  • (B) The address space is rebuilt for the new program.
  • (C) The register set is reinitialised at the new entry point.
  • (D) Control passes to the new program's entry point.

Common misconception. Thinking exec() creates a new process. It creates no process at all: it replaces the calling process's image, which is why the PID is unchanged and why the call never returns on success.

Takeaway. fork() makes a copy, exec() replaces the image, and the PID belongs to the process, not to the program.

OS-U1-Q29MSQmedium

Which of the following statements about process creation and termination in a UNIX-like system are TRUE? (Select all that apply.)

  1. After fork() returns, the parent and the child both continue from the instruction that follows the call.
  2. A successful exec() replaces the process image but keeps the same PID.
  3. A process that has terminated but whose exit status has not yet been collected by its parent is called a zombie.
  4. A zombie process keeps executing in the background and continues to consume CPU time.
Show answer & solution

Detailed solution

Concept. fork() returns twice — once in the parent, with the child's PID, and once in the child, with 0 — and both copies resume at the next instruction. exec() overlays a new program on the existing process. A terminated process whose parent has not yet called wait() stays in the process table as a zombie, holding only its exit status.

Step by step.

  1. (A) is true: fork() duplicates the calling process and both copies continue after the call.
  2. (B) is true: exec() changes the program, not the process identity.
  3. (C) is true: that leftover entry is exactly what "zombie" names.
  4. (D) is false: a zombie has already released its memory and has no code to run, so it uses no CPU. It occupies a process-table slot and nothing else.

Answer: Options (A), (B) and (C).

Common misconception. Confusing a zombie with an orphan. A zombie has died and awaits reaping; an orphan is alive but its parent has died, so it is re-parented to init. Zombies waste table entries, not CPU time.

Takeaway. Read every statement for what it literally says: (D) fails on "keeps executing", not on "zombie".

OS-U1-Q30MCQeasy

What is the primary purpose of the medium-term scheduler (the swapper)?

  1. To decide which of the ready processes runs next on the CPU
  2. To remove a process from main memory temporarily, lowering the degree of multiprogramming and freeing memory
  3. To admit brand-new processes into the system
  4. To decide the order in which pending I/O requests are serviced
Show answer & solution

Detailed solution

Concept. The medium-term scheduler swaps a whole process out of main memory to disk and later back in. It is the tool that turns the five-state model into the seven-state model, adding Ready/Suspend and Blocked/Suspend. Its effect is to lower the degree of multiprogramming without destroying the process.

Step by step.

  1. Swapping a process out of memory is exactly what the medium-term scheduler does — option (B).
  2. Choosing the next ready process is the short-term scheduler.
  3. Admitting new processes is the long-term scheduler.
  4. Ordering I/O requests is disk scheduling, part of the I/O subsystem.

Answer: Option (B) — the medium-term scheduler swaps processes out of memory to reduce the degree of multiprogramming.

Why the other options are wrong.

  • (A) is the short-term scheduler.
  • (C) is the long-term scheduler.
  • (D) is the disk scheduler.

Common misconception. Thinking swapping improves throughput automatically. Swapping relieves memory pressure at the cost of disk traffic, so it can reduce throughput if it is used too eagerly — the thrashing problem of Unit 5.

Takeaway. The medium-term scheduler is the only one that can make a process leave main memory while it is still alive.

OS-U1-Q31NATmedium

Three CPU-bound processes each need exactly 12 ms of CPU time. They are run one after another on a single CPU by a non-preemptive scheduler. Every context switch between two processes costs 0.4 ms and there is no other overhead. What is the total elapsed time, in milliseconds, from the instant the first process starts running to the instant the third process finishes? (Enter a number; one decimal place is allowed.)

Show answer & solution

Detailed solution

Concept. Useful CPU work is the sum of the bursts. On top of that, every switch between two processes costs the dispatch latency. With three processes run back to back there are exactly two switches — P1 → P2 and P2 → P3.

Step by step.

  1. Useful work = 3 × 12 = 36 ms.
  2. Switches between processes = 3 − 1 = 2.
  3. Switch overhead = 2 × 0.4 = 0.8 ms.
  4. Total elapsed time = 36 + 0.8 = 36.8 ms.

Answer: 36.8 ms.

Common misconception. Counting three switches and adding 1.2 ms. The interval measured runs from the start of P1 to the end of P3, so the switch into P1 and the switch out of P3 lie outside it; only the two switches between processes are inside.

Takeaway. Number of context switches between n processes run back to back = n − 1. Multiply by the switch cost and add the useful work.

OS-U1-Q32MCQmedium

The seven-state process model adds Ready/Suspend and Blocked/Suspend to the five-state model. Which one of the following transitions is NOT possible?

  1. Blocked → Blocked/Suspend
  2. Ready/Suspend → Ready
  3. Running → Ready/Suspend
  4. Blocked/Suspend → Ready/Suspend
Show answer & solution

Detailed solution

Concept. In the seven-state model a process leaves the CPU only through the ordinary five-state edges. To be suspended it must first be off the CPU, in Ready or Blocked; only then can the swapper move it to disk. There is therefore no edge that takes a running process straight to a suspended state.

Step by step.

  1. Blocked → Blocked/Suspend: the swapper moves a waiting process out of memory — possible.
  2. Ready/Suspend → Ready: the process is swapped back in — possible.
  3. Running → Ready/Suspend: the running process would have to be both displaced and written out in one step, which the model does not allow — not possible.
  4. Blocked/Suspend → Ready/Suspend: the awaited event completes while the process is on disk — possible.

Answer: Option (C) — Running → Ready/Suspend is not an edge of the seven-state model.

Why the other options are wrong.

  • (A) is the ordinary swap-out of a blocked process.
  • (B) is the ordinary swap-in of a ready process.
  • (D) is the event-completion edge while the process is suspended.

Common misconception. Assuming that suspension is something the scheduler can do to a running process. Suspension is done by the medium-term scheduler to a process that is already off the CPU, and the model always routes it through Ready or Blocked first.

Takeaway. Any transition in this model either leaves or enters the CPU through the five-state edges; the suspend states are reached only from Ready and Blocked.

  • Semaphores. P decrementing and blocking on a negative result, V incrementing and waking one waiter; the negative value as a count of blocked processes; binary against counting semaphores; the final value as initial + #V − #P; and self-deadlock when a non-recursive mutex is re-entered.
  • Classic problems. Bounded buffer with full = 0 and empty = N and the invariant full + empty = N; dining philosophers, the circular wait of the naive solution, and the asymmetric and hierarchy fixes with the ⌊forks / 2⌋ bound; readers–writers and the mirror-image starvation hazards of the two priority directions.
